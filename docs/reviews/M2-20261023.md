## Phát hiện

### [Major] 1. Cache hỏng / clone dở trên Windows không xóa được → `PermissionError` thô, cache kẹt vĩnh viễn, sót thư mục `.tmp-<pid>` — `src/loc_counter/git_repo.py:217`, `:230`, `:235-237`
- **Mô tả**: Git trên Windows tạo file pack/idx/rev/commit-graph với thuộc tính read-only. `shutil.rmtree(..., ignore_errors=True)` không xóa được các file này và nuốt lỗi im lặng. Sau đó `os.replace(tmp, dest)` thất bại vì `dest` vẫn còn (không rỗng), ném `PermissionError` (tiếng Anh, không phải `GitError`); nhánh `except BaseException` gọi lại `rmtree(tmp, ignore_errors=True)` cũng không xóa được → sót `.tmp-<pid>`. Mọi lần `open` sau đều lặp lại lỗi vì `dest` vẫn hỏng.
- **Kịch bản (đã kiểm chứng, v2_rmtree.py)**: repo nguồn có `git gc` → `GitRepo.open` (cache có 4 file read-only: commit-graph, pack-*.idx/.pack/.rev) → xóa `HEAD` trong cache → `GitRepo.open` lần 2 → `PermissionError [WinError 5] Access is denied: '...\6bb304d69d2a831f.tmp-15896' -> '...\6bb304d69d2a831f'`; cache còn lại `['6bb304d69d2a831f', '6bb304d69d2a831f.tmp-15896']`. Tình huống tương tự khi clone bị ngắt giữa chừng sau khi đã nhận pack (tmp còn file read-only).
- **Đề xuất sửa**: hàm `_rmtree_force(path)` dùng `shutil.rmtree(path, onexc=...)` (3.12+) / `onerror` (3.11) để `os.chmod(p, stat.S_IWRITE)` rồi xóa lại; không dùng `ignore_errors=True` cho `dest`. Sau khi xóa, nếu `dest` vẫn tồn tại → `GitError` tiếng Việt ("Không xóa được thư mục cache hỏng <dest>…"). Bọc `os.replace` lỗi `OSError` thành `GitError`. Thêm test TC cho cache hỏng có pack read-only (fixture chạy `git gc` + `os.chmod` read-only để chạy được cả trên Linux).
- **Tham chiếu**: git_repo §5.4 bước 4, 6; §8 (Windows); CLAUDE.md "File tạm/thư mục tạm được dọn"; §15 lỗi tiếng Việt.

## Ghi chú cho spec
(Cần người dùng quyết định — reviewer không tự sửa spec.)
- **S1 — Mâu thuẫn D13 với bảng 5.3 về binary ở `full`.** D13: "`full` — … binary theo `exclude_binary`, file quá lớn vẫn export". Bảng 5.3 dòng "Không lexer, > giới hạn → `full`: export, không đọc nội dung" và "Source, > giới hạn → `full`: export" khiến file binary lớn (`.png`, `.jar`, `.zip` > `max_file_size_kb`) vẫn vào zip dù `exclude_binary=true` — đã kiểm chứng (v1: `big.png` 3 KB và `big.py` toàn NUL với `max_file_size_kb=1` đều được export). Đây lại chính là loại binary phổ biến nhất. Cần chốt: (a) luôn đọc ≥ 8000 byte đầu để kiểm binary kể cả file lớn, hoặc (b) chấp nhận như hiện tại và ghi rõ. Đồng thời làm rõ dòng "Ngôn ngữ trong `exclude_languages` → export" có áp kiểm binary hay không (Major 3 giả định là có, theo bước 3.6/4 và D13).
- **S2 — Câu chữ cảnh báo ở `full`.** Cảnh báo TOO_LARGE/BINARY/UNKNOWN_LANGUAGE dùng chữ "Bỏ qua" dù file vẫn được export (chỉ bỏ khi đếm). Cân nhắc thông báo riêng cho export `full` hoặc ghi rõ ngữ nghĩa "bỏ qua khi đếm" trong spec/README.
- **S3 — Độc lập với cấu hình git toàn cục.** Spec git_repo §8 chỉ nêu `core.quotepath`/`core.autocrlf`. Đề nghị mở rộng: `log.showSignature=false`, `--origin origin` khi clone, và yêu cầu test chạy với `GIT_CONFIG_GLOBAL`/`GIT_CONFIG_NOSYSTEM` cô lập.
- **S4 — Phiên bản git tối thiểu vs. `GIT_CONFIG_PARAMETERS`.** A1 khẳng định git ≥ 2.30 hỗ trợ định dạng đang dùng; cần xác nhận hoặc đổi sang định dạng `'key=value'` / nâng tối thiểu lên 2.31.
- **S5 — Credential helper và timeout.** A2 chấp nhận GCM khi không có token, nhưng chưa nói gì khi **có** token mà token sai (401 → helper vẫn được gọi, có thể bật GUI/treo dưới Streamlit). Spec chưa có timeout cho lệnh mạng.
- **S6 — Làm sạch đường dẫn trong cây git** (`..`, `.git`, `\`) trước khi export/giải nén: cần quy tắc chung cho `snapshot` (M2), `builder` (M4) và bước giải nén/đếm của `pipeline` (M5).
