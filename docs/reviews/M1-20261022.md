## Phát hiện

### [Minor] File config không phải UTF-8 gây traceback thay vì lỗi tiếng Việt — `src/loc_counter/config.py:72`
- Mô tả: `path.read_text(encoding="utf-8")` không bắt `UnicodeDecodeError` (và `OSError` khi không có quyền đọc). Chỉ `yaml.YAMLError` được đổi thành `ConfigError`.
- Kịch bản lỗi (đã kiểm chứng): `config.yaml` lưu bằng Notepad dạng "Unicode" (UTF-16) hoặc ANSI cp1258 có comment tiếng Việt → `loc-counter count <dir> --config config.yaml` in traceback Rich `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xfe...`, mã thoát 1, không có dòng `Lỗi: ...`.
- Đề xuất: bắt `UnicodeDecodeError`/`OSError` quanh `read_text`, ném `ConfigError("File cấu hình phải được lưu dạng UTF-8: <path>")` (cần bổ sung dòng vào bảng §7 của spec `config` trước khi sửa) + 1 TC.
- Tham chiếu: §15 (lỗi tiếng Việt dễ hiểu), spec cli-count §7 "Config lỗi → `Lỗi: <thông báo ConfigError>`".

### [Minor] Thư mục con không đọc được bị bỏ qua im lặng — `src/loc_counter/counter.py:90`
- Mô tả: `os.walk(root, followlinks=False)` mặc định `onerror=None` → lỗi `scandir` (vd. `PermissionError`) của thư mục con bị nuốt, không cảnh báo.
- Kịch bản lỗi (đã kiểm chứng bằng cách giả lập `os.scandir` ném `PermissionError` cho `sub/`): kết quả chỉ có `a.py`, `warnings == []` — LOC bị thiếu mà người dùng không biết.
- Đề xuất: truyền `onerror` ghi `LocWarning(READ_ERROR, <rel dir>, "Không đọc được thư mục: <lỗi>")`. Cần thêm tình huống này vào spec `counter` §5/§7.
- Tham chiếu: checklist 4 "Không nuốt exception im lặng"; §7.5.

### [Minor] Junction (NTFS) bị duyệt như thư mục thường → đếm trùng — `src/loc_counter/counter.py:93`
- Mô tả: `os.path.islink` trả False cho junction; `os.walk(followlinks=False)` cũng chỉ kiểm `islink` → junction được đi vào.
- Kịch bản lỗi (đã kiểm chứng): `real/a.py` + junction `link → real` → bảng in `link/a.py` và `real/a.py`, TỔNG 2 thay vì 1. Junction trỏ về thư mục cha có thể lặp tới khi đường dẫn quá dài (lỗi bị nuốt, xem phát hiện trên).
- Đề xuất: bỏ thư mục có `os.path.islink(p) or os.path.isjunction(p)` (Python ≥ 3.12; với 3.11 dùng `os.lstat(...).st_file_attributes & FILE_ATTRIBUTE_REPARSE_POINT`). Ảnh hưởng chủ yếu lệnh `count` trên thư mục tùy ý; thư mục export từ git (M2+) không có junction.
- Tham chiếu: spec counter §6 "Symlink (file hoặc thư mục) không được theo"; checklist 6.

### [Minor] Chỉ số/tổng dòng lệch so với số dòng vật lý (git) khi file chứa `\f`, `\v`, `\x85`, `\u2028`, `\r` đơn — `src/loc_counter/classifier.py:53`
- Mô tả: kết quả đúng R5 (`len == len(splitlines())`), nhưng `splitlines()` tách nhiều ký tự hơn `\n` mà git dùng để đánh số dòng.
- Kịch bản (đã kiểm chứng): `a = 1\n\x0c\nb = 2\n` (form feed kiểu GNU, có trong nhiều file C/Python cũ): git 3 dòng, classifier 4 phần tử. File cp1252 có `…` (byte 0x85) → giải mã latin-1 thành `\x85` (NEL) → `s = "wait…more"` thành 2 dòng, cả 2 tính code. `\u2028` trong chuỗi JS cũng vậy.
- Ảnh hưởng M1: `total_lines` lệch nhẹ, có thể +1 dòng code ở trường hợp chuỗi chứa ký tự này (spec classifier A1 đã chấp nhận). Ảnh hưởng M4/M5: `added_code`/`deleted_code` (§8.2) tra `is_code[line]` theo số dòng của `git diff`/`blame` → lệch chỉ số từ dòng chứa ký tự đó trở đi. Xem Ghi chú spec S2.
- Đề xuất: không sửa ở M1; quyết định trước khi viết spec `attribution`/`counter` M5.

## Ghi chú cho spec
(Cần người dùng quyết định — không tự đổi thuật toán §6 theo CLAUDE.md quy tắc 2.)

- **S1 — Chỉ thị tiền xử lý bị tính là comment.** Pygments gán `Comment.Preproc` / `Comment.PreprocFile` cho: `#include`, `#define` (C/C++), `#region`, `#if DEBUG`, `#endif` (**C#** — một trong 9 ngôn ngữ bắt buộc §6.4), thuộc tính Rust `#[derive(Debug)]`, thẻ `<?php`; `Comment.Hashbang` cho `#!/usr/bin/env python`. Theo đúng chữ §6.2 ("`Token.Comment.*` → không đánh dấu") các dòng này **không** là code, trong khi theo ý §3.4 và theo `cloc` chúng là code. Đã kiểm chứng: `#region X / using System; / #if DEBUG / int x = 1; / #endif / #endregion` → `[F, T, F, T, F, F]`; `#include <stdio.h> / #define N 10 / int main()...` → `[F, F, T]`. Phương án: (a) giữ nguyên §6.2 và ghi vào README như D4; (b) coi `Comment.Preproc`, `Comment.PreprocFile` (và có thể `Comment.Hashbang`) là code. Đề xuất (b) cho `Preproc*`, vì đây là chỉ thị biên dịch chứ không phải chú thích. Nên ghi thành câu hỏi mở Q10 trong PLAN.md; nếu chọn (b) cần sửa spec `classifier` (R4, mục 5, thêm TC cho C#/C).
- **S2 — Đơn vị "dòng" giữa classifier và git.** §6.2.4 dùng `len(content.splitlines())`, còn diff/blame ở §7–§8.2 đánh số theo `\n`. Hai cách này khác nhau khi file chứa `\f`, `\v`, `\x1c`–`\x1e`, `\x85` (hay gặp khi file cp1252 bị giải mã latin-1), `\u2028`, `\u2029`, `\r` đơn. Cần chốt trước M4/M5: hoặc ánh xạ chỉ số theo `\n` (tách bằng `split("\n")`, coi `\r\n` là một), hoặc chuẩn hóa ở tầng gọi. Spec classifier A1 hiện chỉ nói "rất hiếm" nên chưa tính tới việc lệch chỉ số khi ghép với diff.
- **S3 — Tiêu chí M1 so với cloc.** Báo cáo test M1 ghi Python lệch +3,15% (> 2% theo §13), do cloc coi mọi chuỗi triple-quote là comment còn §3.4 coi chuỗi dữ liệu là code. Sau khi bỏ phần khác định nghĩa thì còn −0,30%. Người dùng cần xác nhận chấp nhận "Đạt với điều kiện" trước khi chuyển spec sang `reviewed` và đóng M1.
- **S4 — Bổ sung xử lý lỗi vào spec** (theo Minor #1, #2): `config` §7 thêm "file không phải UTF-8 / không đọc được"; `counter` §5/§7 thêm "thư mục con không đọc được → cảnh báo" và "junction không được theo".
- **S5 — `exclude_dirs` chứa `/`** (vd. `src/generated`) không bao giờ khớp vì chỉ so từng thành phần tên thư mục; spec `filters` chưa nói. Nên ghi rõ "chỉ tên một thư mục" hoặc hỗ trợ đường dẫn tương đối.
