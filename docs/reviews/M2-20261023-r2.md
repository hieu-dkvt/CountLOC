### [Minor] 1. Có token nhưng sai vẫn có thể bật hộp thoại / treo qua `GIT_ASKPASS` (`core.askPass`, `SSH_ASKPASS`) — `src/loc_counter/git_repo.py:195-205`
- **Mô tả**: Spec §8 và A2 khẳng định "có token thì credential helper bị tắt nên không treo ở hộp thoại". `credential.helper=` chỉ tắt helper; khi server trả 401, git vẫn gọi chương trình askpass (thứ tự `GIT_ASKPASS` → `core.askPass` → `SSH_ASKPASS`) bất kể `GIT_TERMINAL_PROMPT=0` (biến này chỉ chặn prompt terminal). Terminal tích hợp của VS Code đặt sẵn `GIT_ASKPASS` → chạy `uv run streamlit …` từ đó với token sai sẽ hiện ô nhập username trong VS Code và lệnh git đứng chờ.
- **Kịch bản (đã kiểm chứng, v_askpass.py)**: server HTTP cục bộ luôn trả 401; env giống code (`GIT_TERMINAL_PROMPT=0`, `GIT_CONFIG_PARAMETERS="'credential.helper='"`) + `GIT_ASKPASS=<script ghi file đánh dấu>` → `git ls-remote` gọi script **2 lần** (username, password). Với `GIT_ASKPASS=""` (kể cả khi đặt `SSH_ASKPASS`) → không gọi askpass, lỗi ngay `could not read Username … terminal prompts disabled` (được `_AUTH_RE` phân loại đúng). Hành vi với VS Code cụ thể: chưa kiểm chứng.
- **Đề xuất sửa**: khi có token, thêm `env["GIT_ASKPASS"] = ""` (git coi chuỗi rỗng là "đã đặt" nên bỏ qua cả `core.askPass` và `SSH_ASKPASS`). Bổ sung vào spec 5.1.2 và assert trong TC-16.
- **Tham chiếu**: git_repo §5.1.2, §8, A2; spec gốc §15.

### [Minor] 2. Xóa cache hỏng làm thay đổi thuộc tính file của repo nguồn local (hardlink) — `src/loc_counter/git_repo.py:148-150`
- **Mô tả**: Repo local được clone bằng hardlink (spec §8). Trên Windows thuộc tính read-only gắn với file chứ không với từng link, nên `os.chmod(target, S_IWRITE)` trong `_remove_tree` bỏ read-only của chính file pack/idx/rev trong `.git/objects` của repo nguồn. Không mất dữ liệu (git không phụ thuộc cờ này) nhưng trái với cam kết "repo nguồn không thay đổi" (TC-git_repo-04) và bảo vệ chống ghi nhầm của git.
- **Kịch bản (đã kiểm chứng, v_hardlink.py)**: repo nguồn sau `git gc` có `.idx/.pack/.rev` read-only → `GitRepo.open` (cache `st_nlink == 2`) → xóa `HEAD` của cache → `open` lại → ba file trong repo **nguồn** chuyển `writable=True`.
- **Đề xuất sửa**: vì thuộc tính read-only dùng chung giữa các hardlink nên không thể vừa xóa link vừa giữ nguyên file nguồn bằng chmod. Hai phương án: (a) clone local với `--no-hardlinks` (cache độc lập, tốn đĩa/thời gian hơn); (b) giữ hardlink, trong `retry` ghi nhớ file có `st_nlink > 1`, sau khi xóa link thì khôi phục read-only cho link còn lại là không làm được từ cache → chấp nhận và ghi thành giả định trong spec. Cần người dùng quyết — xem Ghi chú spec S2.
- **Tham chiếu**: git_repo §5.4 bước 4, §8 "Clone local dùng hardlink"; TC-git_repo-04.

### [Minor] 3. `write_zip` lỗi giữa chừng để tiến trình `git cat-file --batch` sống tiếp — `src/loc_counter/snapshot.py:196-211`
- **Mô tả**: generator `blobs` không được `close()` khi có exception; traceback giữ frame `write_zip` → generator → `Popen`. Chừng nào đối tượng exception còn được giữ (UI lưu lỗi vào state, log `exc_info`, test `pytest.raises`), tiến trình `cat-file` vẫn chạy và giữ handle tới file pack trong cache (Windows không xóa được cache — đúng loại lỗi của Major 1 lần trước).
- **Kịch bản (đã kiểm chứng, v_leak.py)**: plan 3 file, `ZipFile.writestr` ném `OSError(28)` → bắt `SnapshotError` và giữ lại → `cat-file alive: [True]`; chỉ sau `del` + `gc.collect()` mới `[False]`.
- **Đề xuất sửa**: `finally: if hasattr(blobs, "close"): blobs.close()` (hoặc `contextlib.closing`) trong `write_zip`; tương tự an toàn cho mọi nơi tiêu thụ `read_blobs` dở dang.
- **Tham chiếu**: checklist §6 "không giữ handle file mở"; snapshot §5.4 bước 1.

### [Minor] 5. `commit_info` vẫn phụ thuộc cấu hình toàn cục `i18n.logOutputEncoding` — `src/loc_counter/git_repo.py:29-30`, `:351-352`

## Ghi chú cho spec
(Cần người dùng quyết định — reviewer không tự sửa spec.)
- **S1 — Mở rộng định nghĩa "đường dẫn không an toàn"** (snapshot 5.3.3.2, A1) cho Windows: thành phần có `:` (ổ đĩa, ADS), ký tự cấm `<>"|?*`, kết thúc bằng `.`/khoảng trắng, `.git` sau khi bỏ `.`/khoảng trắng cuối; và quy tắc chung cho M4/M5 về entry trùng nhau sau khi Windows chuẩn hóa (`A.py` vs `a.py`, `a:b.py` vs `a_b.py`) khi giải nén để đếm (Minor 6).
- **S2 — Hardlink khi clone local** (git_repo §8, PLAN D12): chọn (a) giữ hardlink và chấp nhận `_remove_tree` bỏ read-only trên file object của repo nguồn, ghi thành giả định; hay (b) `git clone --no-hardlinks` (không đụng repo nguồn, tốn đĩa/thời gian hơn) (Minor 2).
- **S3 — Đọc trọn file lớn ở `full`**: spec 5.3 bước 3.6/4 yêu cầu đọc mọi ứng viên để kiểm binary; `read_blobs` đọc toàn bộ blob vào RAM (file 2 GB → 2 GB RAM), rồi `write_zip` đọc lại lần hai. Spec §8 đã để M7, nhưng nên ghi rõ giới hạn hoặc cho phép đọc phần đầu (`git cat-file blob` dạng stream, dừng sau 8000 byte) cho file vượt `max_file_size_kb`.
- **S4 — A2 / §8 về hộp thoại xác thực**: bổ sung `GIT_ASKPASS=""` khi có token; quyết định có áp cả khi **không** có token hay không (hiện A2 cho phép GCM hỏi người dùng) (Minor 1).
- **S5 — Danh sách cấu hình toàn cục bị ghi đè** (§8): thêm `i18n.logOutputEncoding=UTF-8`; cân nhắc `http.extraHeader` sẵn có trong cấu hình người dùng (git gửi cả hai header `Authorization` — chưa kiểm chứng với GitHub).
